    • 1. Purpose and scope

    The MVSS system is intended to help the school manage student information, academic performance, attendance, fees, staff information and related administrative activities in one place. It is designed to remain usable when internet connectivity is unavailable and to synchronise changes with the online database when connectivity returns.

    The system supports a school population of approximately 4,000 students. Actual capacity and performance depend on the device, browser, data volume, network quality and implementation of the current version.

    2. Important operating principles

  • Use a supported, up-to-date browser and keep the device charged.
  • Use the school-approved system address. Avoid unofficial copies or downloaded HTML files for routine use.
  • Allow the application to finish loading before entering or editing records.
  • Save or submit each record using the control provided by the page; do not assume that typing alone saves it.
  • Check the sync indicator after important work, especially after reconnecting to the internet.
  • Do not clear browser site data, IndexedDB, cache or application storage as a troubleshooting shortcut. These may contain unsynchronised offline work.
  • Do not edit the same student or record simultaneously on multiple devices unless the school has confirmed that the current sync design safely supports that workflow.
  • Keep a separate verified backup before major changes, upgrades or restoration.

    • 3. Opening the system and signing in

  • Connect to the internet for the first visit or when a new version must be downloaded.
  • Open the official school system website in the browser.
  • Wait for the dashboard or sign-in screen to appear.
  • Enter the authorised school login details and submit.
  • Confirm that the expected school data and navigation options are visible.

    • Shared login: The current arrangement uses one shared staff login. Keep the credentials confidential and ensure only authorised staff use the account. Because actions may not be attributable to an individual, the school should maintain a separate written record of who performs sensitive tasks.

    Security: Never send passwords in group chats or include them in screenshots shared with support.

    4. Dashboard and navigation

    The dashboard is the starting point for navigating available system modules. Depending on the deployed version, it may provide links or summaries for students, classes, academic records, attendance, fees, staff, resources, communications, settings and backups.

  • Review dashboard notices and system status before beginning work.
  • Choose the module that matches the task.
  • Use the page's search, filter or class selector where available.
  • Return to the dashboard using the navigation control provided by the system.

    • If a menu is missing: The page may not be included in the current build, may be hidden by permissions, or may have a different label. Contact the system administrator rather than creating duplicate records elsewhere.

    5. Finding a student

  • Open the student list, student records or equivalent page.
  • Search using the student's Student ID or another supported identifier.
  • If available, narrow the results by name, class or year.
  • Open the matching student and verify at least two identifying details before editing.

    • Good practice: Avoid selecting a student using name alone where similar names exist. Student ID is the preferred reference when available.

    6. Student registration and editing

    Use the student registration form to create a new student record and the edit function to correct an existing record. Enter information carefully and review it before saving.

    • Report cards: Identification and support details described above are intended for the student record/archive and should not be added to report cards unless the school explicitly requires and approves that change.

    7. Student archive and identification details

    The archive is the historical reference for a student's information. Search by Student ID, open the correct student and review the available sections. Where implemented, the archive should show identification details, parent contacts, DOB, medical/support fields, and academic history.

  • Review marks by the specific academic year and term.
  • Review each subject separately.
  • Check Activities of Integration alongside the relevant subject and term.
  • Use the archive to verify historical information; do not overwrite an old term's marks to enter a new term's results.

    • Missing archive data: If a section is blank, first confirm the correct student, year and term. If the information was never entered or is not supported in the deployed version, report it to the administrator.

    8. Classes and class lists

  • Open the classes or class list module.
  • Select the correct academic year, class and stream if those filters are available.
  • Check the student count and names against the school's approved register.
  • When exporting or printing, confirm the selected class and date range before producing the document.

    • Data quality: Resolve duplicate student entries and incorrect class placements through the authorised edit process. Do not delete a student record merely because the student has transferred or left; follow the school's archive/withdrawal procedure.

    9. Subjects, marks and Activities of Integration

  • Select the correct academic year and term.
  • Select the class and subject.
  • Confirm that the assessment is being entered for the correct students.
  • Enter marks in the appropriate fields, including Activities of Integration where provided.
  • Review totals, ranges and missing entries before saving.
  • Reopen a sample of saved records and confirm that the marks appear under the intended subject and term.

    • Critical check: Never enter marks while the wrong term, class or subject is selected. Do not assume an autosave occurred; look for the page's save confirmation or verify the saved result.

    Archive: Historical results should remain associated with their original term and subject, including Activities of Integration, so that the archive can display the correct academic history.

    10. Terms and academic periods

    Term settings determine the academic period to which marks and other records belong. Before opening marks entry, verify the current year and term. Only authorised administrators should change term settings, because an incorrect setting can place new records in the wrong academic period.

  • Confirm the academic year.
  • Confirm the term name/number and dates, if configured.
  • Tell staff when the active term changes.
  • Do not alter a closed term simply to make a new entry easier; consult the administrator.

    • 11. Student attendance

  • Open student attendance.
  • Choose the correct date, class and session.
  • Mark each student according to the school's attendance codes.
  • Review absences and late arrivals before saving.
  • Confirm that the saved attendance is displayed for the correct date.

    • Where attendance notes or reasons are supported, enter concise factual information and follow the school's privacy policy.

    12. Class attendance

    If the system has a separate class attendance page, use it for class-level attendance tasks. Verify the class, date and session before entering data. Avoid recording the same attendance twice in different modules unless the system's workflow specifically requires it.

    13. Fees and payment records

  • Open the fees or finance module.
  • Find the student using Student ID and verify the student's identity.
  • Review the displayed balance and previous transactions.
  • Enter the payment or adjustment using the school's approved procedure and required reference details.
  • Save the transaction and verify that the balance/transaction history updates.

    • Financial control: Only authorised personnel should record, edit or reverse financial transactions. Keep official receipts and reconcile system entries with the school's approved cashbook/bank/mobile-money records. Do not use the system as a substitute for statutory accounting records.

    14. Teacher and staff records

    Use the staff or teacher records module, where available, to view or maintain staff details. Check names, contact details, roles and assigned responsibilities. Limit access to confidential staff information to authorised personnel.

    15. Payroll

    If payroll functions are enabled, confirm the correct staff member and pay period before entering or reviewing figures. Payroll information is confidential. Verify calculations and approvals against the school's official payroll process before payment.

    Caution: This manual does not certify payroll calculations, statutory deductions or payment integrations. Have the responsible finance officer verify these independently.

    16. Resources and documents

    Use the resources/documents area, where available, to access school files and shared materials. Check that a document is current before relying on it. Do not upload confidential documents to a broadly accessible area unless access controls have been checked.

    17. Parent letters and parent communication

    Where parent letters are supported, select the intended student, class or recipient group carefully. Preview the letter before printing or sending. Check names, dates, amounts and contact information. Keep a copy of important notices according to school policy.

    18. Parent attendance and portal

    If parent attendance or a parent portal is enabled in the deployed version, use the relevant page to review only the information intended for that parent or guardian. Do not share another student's information. Test parent-facing access with an authorised test account before wide distribution.

    19. Staff communication

    Use the staff communication module, if enabled, for school-related notices. Keep messages professional, factual and relevant. Avoid posting passwords, sensitive student information or confidential financial details in general staff messages.

    21. Library management and book returns

    Open Library Management from the dashboard. A librarian account is created by an administrator in Teachers & Staff by selecting the Librarian role and saving the librarian's registered phone contact. The librarian signs in by choosing Librarian and entering that same registered contact.

    • Enter the student's ID; the registered student name is filled automatically.
    • Record the book ID, title, number of books, date taken and expected return date. The return date must not be earlier than the date taken.
    • Use Mark Returned only after the physical book has been received. A green tick means returned; a red cross means outstanding.
    • Use the student archive search to view the student's complete borrowing history and identify books not returned.
    • Book loans are included in the same local/cloud database synchronisation and database backup as other records.

    22. Printing CAI by subject

    For Senior Three or Senior Four, open the CAI/AOI section or the class page and choose Print CAI or Download CAI PDF. Select the exact saved subject and the required term. The register includes every student registered in that class; students without a saved mark for that subject are shown with blank mark cells. SC is marked out of 10 and GC out of 5 at every level; the number of levels is not fixed. CAI remains separate from the report card.

    23. Staff login and session persistence

    Administrators register each staff member's contact and role in Teachers & Staff. Teachers and librarians must choose their matching role and enter the exact registered contact. Unregistered contacts or contacts registered under a different role are rejected. This contact check is a basic directory match, not a one-time-password identity check. The application does not currently sign staff into individual Firebase Authentication accounts. Protect devices and exported backups, and ensure Firestore security rules are not publicly open.

    After a successful login, the browser keeps the session across page refreshes until Logout is selected or the staff/student account is no longer valid. On shared devices, always use Logout before leaving the device.

    24. Report card watermark

    The report card is printed without the large diagonal MVSS watermark. Its existing report-card layout and academic content are otherwise retained.

    20. Offline use and online synchronisation

    Shared records use Firebase Cloud Firestore only. The application does not load Firebase Cloud Storage, Firebase Storage uploads, Cloud Functions or paid server components. Keep the Firebase project on the no-cost Spark plan and stay within the Firestore free quota. Local backups are downloaded separately and are not cloud backups.

    The system is designed as an offline-first web application. Once the application has loaded and its offline resources have been cached, records can be entered locally without internet and synchronised to Firestore when connectivity returns. Data is saved locally first and synchronised through Firebase Firestore when internet is available. Other devices connected to the same Firebase project receive shared updates, subject to the project’s Firestore security rules.

  • While online, open the official website and allow it to finish loading.
  • Confirm that the offline-ready application is loaded before relying on it without internet.
  • If internet is lost, continue only with functions that remain available. Do not assume every external service or feature works offline.
  • When internet returns, keep the app open and allow synchronisation to complete.
  • Check the sync status and verify important records on a second online check or after refreshing only when the sync status indicates it is safe.

    • Conflict warning: A message such as 'Sync conflict - local edits protected' means the application has detected a possible mismatch and is protecting local changes. Stop making further edits to the affected data. Do not clear browser data, force an overwrite, reinstall the app or repeatedly refresh. Contact the system administrator and preserve both local and cloud copies before any recovery.

    Current sync design: The system synchronises the school database as a whole snapshot. Online student editing now uses a shared Firestore lock so only one device at a time can open a particular student's edit form. Locks renew while the form is open and expire automatically after a device stops renewing them. The cloud snapshot publisher also uses an atomic version check to prevent a late concurrent upload from silently replacing a newer cloud snapshot. Because the database is still stored as one snapshot, simultaneous edits to different records can still produce a protected sync conflict that requires administrator review; this version does not automatically merge all database records. Offline editing of an existing student is blocked because a shared lock cannot be checked offline.

    21. Backups and restoration

    A backup is a separate copy of school data that can be used if the live database is damaged, data is deleted or a device is lost. A sync indicator is not a backup. A backup should include all required records, not only student names.

  • Student identification and contact details.
  • Class and enrolment information.
  • Marks for each subject and term, including Activities of Integration.
  • Fees and payment records.
  • Attendance and relevant school activities.
  • Other records required by the school's retention policy.
  • Open the backup/export function provided by the current system.
  • Choose the complete backup option where available.
  • Wait for the export to finish; do not close the page mid-process.
  • Save the file to an approved secure location, not only on the device used to create it.
  • Use a clear filename with school, date and backup type.
  • Check that the file exists and has a plausible non-zero size.
  • Keep a second copy in a separate secure location.

    • Restoration: Restore only under the direction of the authorised administrator. First preserve a copy of the current live data and the backup being restored. A restore may replace current records. Test restoration with a copy or test environment where possible.

    PDF exports: A class PDF is useful for printing and review but may not be a complete machine-restorable database backup. Keep the system's full data export as well.

    22. Monthly backup responsibility

    The school procedure requires one designated person to perform the official monthly backup for each month. This reduces duplicate or conflicting backup actions.

  • At the start of the month, confirm who is assigned as the backup person.
  • Only that designated person should perform and certify the official monthly backup.
  • Complete the backup after checking that current records have synchronised, where possible.
  • Verify the exported file and store it in the approved secure locations.
  • Record the date, time, file name, storage location and responsible person in the backup log.
  • Notify the administrator when the backup is complete.

    • Reminder: A monthly reminder is configured for the first day of each month at 9:00 AM Africa/Kampala, starting 1 December 2026. The site may also display an in-app reminder if that feature is present in the deployed build. A reminder does not itself create or verify a backup.

    23. Data protection and shared login

  • Use the shared login only for authorised school work.
  • Do not disclose login credentials to students, parents or unauthorised persons.
  • Lock the device when leaving it unattended.
  • Do not save student exports on public or shared devices unless they are protected and removed according to school policy.
  • Share only the minimum student information needed for a task.
  • Keep backup files encrypted or in access-controlled storage where possible.
  • Report suspected unauthorised access, data loss or incorrect disclosure immediately.
  • Because staff share one login, maintain a separate activity/approval log for sensitive actions such as marks changes, fee adjustments, bulk imports and data restoration.

    • When offline, every saved edit requires the configured offline authorisation code. The default is set by the school administrator. Archive searching is view-only for parents and teachers; parents are limited to their own student. Only administrators may edit archive information.

    27. Known limitations and safe-use checklist

    The following points should be treated as operational cautions until verified in the deployed system:

  • The app's exact feature set and page labels may change between versions.
  • Offline availability depends on the browser having loaded and cached the app shell and on the relevant feature being implemented for local storage.
  • Firestore synchronises records between devices while the project remains within its free Spark quotas and Firestore security rules allow access.
  • Whole-database snapshot synchronisation can create conflicts when multiple devices edit at the same time.
  • The shared staff login does not provide reliable individual accountability.
  • A visible 'synced' status should be checked against the actual presence of recently entered records when a conflict or missing-data issue has occurred.
  • Backups must be exported and independently verified; synchronisation alone is not a backup.
  • This manual does not certify that every module, permission or backup restore workflow has been tested in production.

    • Quick safe-use checklist

  • ☐ Correct website and authorised login used.
  • ☐ Correct student, class, subject, year and term selected.
  • ☐ Changes saved and verified after entry.
  • ☐ Sync status checked after internet returns.
  • ☐ No conflict warning ignored.
  • ☐ Monthly backup performed by the designated person and independently verified.
  • ☐ Backup stored securely in at least two approved locations.
  • ☐ Developer contacted before risky recovery or overwrite operations.
